# lxd2 — Rust CLI & print server for LX-D02/LX-D2 Bluetooth thermal printers

**Date:** 2026-07-27
**Status:** Approved design, pre-implementation

## Goal

A Rust CLI tool for macOS that prints to LX-D02/LX-D2 Bluetooth thermal printers
(normally driven by the proprietary "FunnyPrint" iOS app), plus a server mode and,
later, a Web Bluetooth web app. Feature set modeled on the author's existing
[printa](https://github.com/cicloid/printa) project (ESC/POS network printers):
text, markdown, images, QR codes, and URL-to-print.

## Printer facts (from protocol research)

Confirmed independently by three open-source implementations
([rusq/thermoprint](https://github.com/rusq/thermoprint) — Go,
[ValdikSS/printer-driver-funnyprint](https://github.com/ValdikSS/printer-driver-funnyprint) — Python/CUPS,
[paradon/lxprint](https://github.com/paradon/lxprint) — TypeScript/Web Bluetooth):

- **BLE profile** (generic serial-over-BLE, JDY/HM-10 style):
  - Service `0xFFE6`
  - Write characteristic `0xFFE1` (host → printer, write-without-response)
  - Notify characteristic `0xFFE2` (printer → host)
  - Advertised name starts with `LX`; no distinctive service UUID in advertisement
- **Geometry:** 384 px wide (48 bytes/line), 203 dpi, 48 mm printable on 58 mm stock
- **Image format:** 1-bit, MSB-first, bit 1 = black, raw rows (no compression)
- **Framing:** `5A <cmd> …` control packets; `55 <idx:u16be> <96B bitmap> 00` raster
  packets (100 bytes, two print lines each, index from 0)

### Command set (host → printer on 0xFFE1)

| Command | Bytes | Meaning |
|---|---|---|
| Hello | `5A 01 …` | Reply contains printer MAC at offset 4..10 |
| Auth challenge | `5A 0A` + 10 random bytes | Reply `5A 0A` + 10 bytes (unused) |
| Auth response | `5A 0B` + 10 bytes | Reply `5A 0B 01` = success |
| Density | `5A 0C <n>` | Darkness 1–7 |
| Print start | `5A 04 <len:u16be> 00 00` | len = number of raster packets |
| Print end | `5A 04 <len:u16be> 01 00` | Sent after `5A 06` finished notification |

### Notifications (printer → host on 0xFFE2)

| Prefix | Meaning |
|---|---|
| `5A 02` | Status: battery %, no-paper, charging, overheat, low-batt, density, voltage |
| `5A 05` | Lost packet — resend starting from index − 1 |
| `5A 06` | Printing finished — respond with print-end |
| `5A 07` | Cooldown — brief pause |
| `5A 08` | Hold — pause streaming until a `5A 05` arrives |

### Auth handshake

Challenge–response keyed on the printer's own MAC (learned from the Hello reply):
for each of 10 random challenge bytes `C[i]`, compute
`crc16_xmodem([C[i], mac[0..6]])` (poly `0x1021`, init `0`) and send the 10 high
bytes as `5A 0B` payload. Implement properly (paradon-style random challenge), not
rusq's hard-coded capture replay which only works on his unit.

Notes: there is no feed command — feeding is printing blank lines. There is no
checksum on the wire besides the auth CRC. Inter-packet delay in the references is
7–20 ms; exact timing to be validated against real hardware.

## Architecture

Cargo workspace, three crates:

```
lxd2/
├── crates/
│   ├── lxd2-core/      # transport-agnostic protocol + rendering core
│   │   ├── protocol    # packet builders/parsers, CRC16 auth, print FSM (sans-IO)
│   │   └── raster      # 1-bit pipeline: dithering, text/markdown layout, QR
│   ├── lxd2/           # CLI binary: btleplug BLE transport, clap, axum server
│   └── lxd2-web/       # (phase 4) WASM build of lxd2-core for Web Bluetooth page
```

**Sans-IO core.** `lxd2-core` never touches BLE. The print job is a pure state
machine:

- `PrintJob::next_action() -> Send(bytes) | Wait(duration) | Done`
- `PrintJob::on_notification(&[u8])`

States (modeled on rusq's `fsm.go`): Idle → Hello → Auth → Ready → Printing ⇄
Paused/Cooldown → WaitingRetry → Completed. The BLE side is a thin async loop that
forwards bytes both ways. This makes retransmit/pause/cooldown logic unit-testable
by replaying recorded notification sequences — no printer needed.

**Transports.** The CLI uses `btleplug` (CoreBluetooth on macOS). The future web
app uses Web Bluetooth via `wasm-bindgen`. Both drive the same FSM.

**Rendering pipeline.** Every input (text, markdown, image, URL, QR) renders to a
384-px-wide 1-bit bitmap, then prints — or saves to PNG with `--preview`. Markdown
via `pulldown-cmark` into a simple layout engine with an embedded font (`fontdue`
or `cosmic-text`); images scaled + dithered (Floyd–Steinberg, Atkinson, threshold);
QR via a pure-Rust QR crate. URL/HTML rendering drives installed Chrome headless at
a 384 px viewport via `chromiumoxide`, feature-gated so the core stays light.

## CLI

```bash
lxd2 scan                          # list nearby LX printers
lxd2 status                        # battery, paper, temperature, density

echo "hello" | lxd2 print          # plain text from stdin
lxd2 print "hello world"
lxd2 print -f notes.md             # markdown
lxd2 print -f photo.png            # image (--dither floyd|atkinson|none)
lxd2 print --url https://…         # headless Chrome screenshot
lxd2 qr "https://example.com"      # QR code, optional caption

# shared options
--device <name|uuid>   # else auto-connect to first LX device / remembered device
--density 1..7
--feed <lines>         # blank-line tear-off margin
--preview out.png      # render to PNG instead of printing
--copies N

lxd2 serve --port 8000             # REST API + embedded web UI
```

Last-used device is remembered in `~/.config/lxd2/config.toml`.

## Server mode

`lxd2 serve` (axum), printa-style endpoints: `POST /print/text`,
`/print/markdown`, `/print/image` (multipart), `/print/url`, `/print/qr`,
`POST /preview/*` (returns PNG), `GET /status`, `GET /health`. A small web UI
(static assets embedded via `rust-embed`) with textarea, image upload, and live
preview — usable from a phone on the LAN while the Mac holds the BLE connection.

## Error handling

- Pre-print status check: refuse on no-paper, warn on low battery.
- Every wait state has a timeout with a specific message
  (`printer stopped responding during print at packet 142/300`).
- Distinct exit codes for: no printer found, no paper, overheated, low battery,
  disconnected mid-print, Chrome not found (URL mode).
- macOS caveat: the terminal app needs a one-time Bluetooth (TCC) permission
  prompt for btleplug to work.

## Testing

- Unit tests: CRC16 and packet encoding against known byte sequences from the
  reference implementations.
- FSM tests: replay captured notification traces (pause, cooldown, lost-packet,
  finish) and assert the action sequence.
- Golden-image tests: `--preview` output compared to checked-in PNGs for text,
  markdown, dithering.
- Hardware validation in phase 1 against the real LX-D2 (timing, retransmit
  semantics differ slightly between reference repos).

## Build phases

1. **Core + minimal print** — workspace, protocol crate with tests,
   `scan`/`status`/`print` for text and images, `--preview`. End-to-end
   validation on real hardware.
2. **Rendering polish** — markdown, QR, dithering options, feed/density/copies,
   config file.
3. **Server** — `serve` with REST + embedded UI, headless Chrome URL printing.
4. **WASM web app** — Web Bluetooth page reusing `lxd2-core` (Chrome/Edge only;
   static hosting, no server).

## Non-goals (for now)

- CUPS/AirPrint integration (ValdikSS and rusq cover this niche; revisit later).
- Cat-printer (0xAE01-family) protocol support — different, incompatible protocol.
- Windows/Linux support is not a target but btleplug keeps the door open.
